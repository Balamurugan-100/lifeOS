# Research: LifeOS Foundation

Phase 0 output — resolves every technical decision for the foundation.
Each entry follows: **Decision** / **Rationale** / **Alternatives considered**.

---

## D-1: Framework and language

**Decision**: Flutter with Dart (stable channel), targeting Android + iOS first.

**Rationale**: The user selected Flutter explicitly. Dart satisfies the
constitution's strong-typing requirement (Principle IV: sound null safety,
strict analyzer lints), Flutter is fully offline-capable (Principle III),
and the widget tree maps cleanly to the modular package structure (Principle
I). Both mobile-first (clarification Q1) and future desktop/web targets are
coverable without a rewrite.

**Alternatives considered**: React Native + TypeScript (weaker local-first
and tooling story on desktop, and the project chose Flutter); native
Kotlin/Swift (two codebases, violates Principle II simplicity); Tauri/Rust +
TypeScript (two languages, more complexity).

## D-2: Domain module architecture

**Decision**: A monorepo of Dart packages using path dependencies — `core`
(contracts + registry), `storage`, one package per domain (`tasks`,
`habits`), `export`, and an `app` shell. No third-party workspace tooling in
v1.

**Rationale**: Package boundaries are the only mechanism that enforces
*Modular Domain Autonomy* (Principle I) at the compile level: a domain
cannot import another domain's internals unless it declares it, and the app
shell can only reach domains through the `core` contracts (FR-006, FR-012).
Each domain stays independently compilable and testable (Principle IV).
Path dependencies avoid workspace-tooling complexity (Principle II).

**Alternatives considered**: Feature-folder layout inside one package
(faster to start, but nothing prevents cross-domain imports — fails
Principle I); using melos for workspace orchestration (nice-to-have, but an
extra dependency; deliverables are identical in v1); publishing domains to
pub.dev (premature for a personal app).

## D-3: Local persistence

**Decision**: SQLite via `drift`, with `sqlite3_flutter_libs` for the native
engine, typed table classes generated by `build_runner`.

**Rationale**: SQLite is the standard offline-first embedded database and is
fully local (Principle III). Drift adds compile-time-typed tables and
queries (Principle IV) and an in-memory database mode that makes repository
tests fast and hermetic. Being SQL-based leaves a realistic migration and
future-sync path (principle "local-first, designed for the future").

**Alternatives considered**: Hive/Isar (key-value/object DB with good
performance, but weaker relational modeling and smaller migration story);
raw `sqflite` (no codegen, error-prone SQL strings — weaker typing
guarantees); JSON files on disk (no queries or integrity enforcement);
`shared_preferences` (not suited to structured data volumes).

## D-4: State management

**Decision**: `flutter_riverpod` (without the codegen package).

**Rationale**: Riverpod gives typed, testable providers and clean
dependency injection for the module registry and database — a good match for
the explicit-boundaries principle (Principle IV). Running it without
generators keeps the build simple (Principle II) while preserving full type
safety.

**Alternatives considered**: Bloc (more ceremony/boilerplate for this UI
scale); `provider` + ChangeNotifier (less structured, weaker DI story across
packages); GetX (convenient but muddles implicit state and reduces
testability); manual callbacks/InheritedWidget (scales poorly as domains
multiply).

## D-5: Identifiers and time (sync-readiness)

**Decision**: UUID (v4) string ids for all entities; calendar-date semantics
(local timezone) for task due-dates and habit dates; `created_at` /
`updated_at` UTC timestamps on every entity; export carries a
`schemaVersion` + `exportedAt`.

**Rationale**: Sync-readiness (Principle III + Assumptions) requires ids that
cannot collide when data later merges from another device — UUIDs provide
that. Local calendar dates match how users think about habits/tasks
("today", "every Monday") and keep v1 timezone handling simple (Assumptions).
`updated_at` timestamps are the minimal hook a future conflict-aware sync
will need, without building the sync now (Principle II).

**Alternatives considered**: Autoincrement integer ids (collision-prone in a
future multi-device world — would force a migration rewrite, violating the
sync-readiness constraint); epoch-millis timestamps for dates (breaks "local
day" semantics and timezone illusion); UTC date-only (correct but surprising
for streak logic when the user crosses midnight).

## D-6: Habit schedule and streak model

**Decision**: Preset schedule model — a habit carries one of (a) daily, or
(b) weekly with a set of 1–7 selected weekdays. Streaks are derived from
`HabitEntry` rows on scheduled days only, never from unscheduled days.

**Rationale**: Matches clarification Q4 exactly ("daily plus preset
frequencies") and keeps the data model and streak logic small (Principle II).
Counting only scheduled days makes weekly habits report honest streaks and
matches the edge-case rule added during clarification ("unscheduled days
never count as missed").

**Alternatives considered**: Fully custom recurrence rules (e.g., every-3-days)
— a recurrence engine is more complexity than v1 needs (rejected under
Principle II); daily-only — too limiting for real habits like "work out 3× /
week" (rejected against clarification Q4); no schedule at all (journal-style)
— weaker product value and would not exercise the schedule logic.

## D-7: Export

**Decision**: One-tap export producing a single portable, human-readable
JSON envelope (all domains, schema-versioned), offered to the user through
the native share sheet so the file can be moved off the device; export-only,
no import in v1.

**Rationale**: Satisfies clarification Q5 and FR-013/SC-009 with one action.
JSON is readable by humans and machines, versioned against `schemaVersion`
for future import/migration, and trivially parseable by a future sync
backend or AI tooling (Principle III). The share sheet is the standard
mobile path for "move this off the device."

**Alternatives considered**: CSV (not a single faithful representation of
nested/relational data); ZIP of multiple files (more to build and harder to
inspect); automated on-device backups with retention (extra storage-
management logic — deliberately deferred); no export in v1 (rejected:
data-safety trust property, clarification Q5).

## D-8: Testing strategy

**Decision**: Per-package `flutter_test` suites (unit tests for domain logic
and repositories against an in-memory drift database, widget tests for the
home screen) plus one `integration_test` suite through the real app shell
covering the five user stories. No network is used anywhere.

**Rationale**: Matches the constitution's automation requirement (Principle
IV) and the spec's measurable criteria (SC-001..SC-009). In-memory drift
keeps repository tests fast and dependency-free (Principle II). The
integration suite is the verifier for user stories 1–5 and the offline/
persistence criteria.

**Alternatives considered**: Mock-centric unit tests for repositories (more
code, tests the mocks more than the code — in-memory DB is simpler and more
faithful); golden-image-only testing (fragile, low signal on logic);
relying only on manual QA (fails Principle IV).

## Constitution check post-design

Re-evaluated after the Phase 1 design (data model + contracts): the design
keeps domains decoupled at the package level (I), avoids new abstractions
and dependencies beyond the minimal set (II), stores only local data with
sync-ready ids/timestamps and no network calls (III), uses typed contracts
with per-package automated tests (IV), and records every decision here for
incremental delivery (V). **Gate remains PASS — no violations introduced.**
